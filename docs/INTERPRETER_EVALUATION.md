# Interpreter evaluation

Generated by `npm run eval:interpreters -- --write` on 2026-10-23, with the model `qwen2.5:3b-instruct` served at localhost:11434 with a timeout of 30000 ms. Rerun it to reproduce; the rules interpreter's numbers are deterministic, the model's may vary between runs and model versions.

30 customer messages, labelled by hand before either interpreter was run on them (data/evaluation/interpreter-paraphrases.json). Each field is scored separately:

- **goal**: return, exchange or not stated.
- **reason**: defective, changed mind, or not stated.
- **product**: the extracted product query finds exactly the labelled order in the fictional sandbox (or no product is extracted when none is named).
- **time hint**: a purchase time is picked up when, and only when, the message states one.

Serial and order numbers are not scored: they always come from the rules interpreter. The model assisted reading takes the goal from the rules interpreter when it found one and from the model otherwise, accepts the model's reason only with a quote that appears in the message, uses the model for product, issue description and purchase time, and the rules interpreter for everything else. When the model fails (invalid output, HTTP error, timeout), the service uses the rules reading, and so does this score.

## Limitations

- 30 messages, written and labelled by the same team that built the interpreters. They are a check of field extraction on plausible phrasings, not a measurement of real customer language.
- Some labels are judgement calls (for example, whether discomfort is a change of mind). They were fixed before any run and are not changed after.
- A reason is a customer claim, but it selects the policy rule, and so the shipping terms of the proposed return. In this run the model supplied a reason the customer did not state on 4 message(s) (P02, P23, P25, P29). The proposed terms, including the reason, are shown to the customer before approval, but a wrong reason is still a real risk of using a model here.
- Better reading does not change what AFTERCARE may do. Every decision still comes from the compiler, and every identifier still comes from the customer's own text.

## What changed, and what it did not fix

Two changes were made on 2026-10-23, on principle and without changing any label: the rules goal is kept whenever the rules interpreter found one, and a model reason counts only when its `reasonQuote` appears in the message (ignoring case and spacing).

- **Goal:** 26/30 before, 29/30 after. The three goal errors that came from the model overriding a correct rules goal (P07, P11, P21) are gone.
- **Reason:** 27/30 before, 24/30 after, and the number of messages where the model stated a reason the customer never gave rose from 2 to 4 (P02, P23, P25, P29). The quote check stops a reason supported by words that are not in the message, but this model often quotes the request itself. In a separate check run on the same day, it gave "Return the headphones please." as the quote for "defective" on P23 and "I want to return my wireless headphones." for "changed_mind" on P02. Those words are in the message, so the check accepts them, although they say nothing about a reason. The check tests that the quote is real, not that it supports the reason.
- **All four fields:** 22/30 both times.
- The run took 228.3 seconds against 96.5 the day before, on the same machine; the longer reply format and machine load both may contribute, and this was not separated.

On this set, the reason grounding did not reduce unstated reasons with this small model. It is kept because it costs nothing when the model quotes honestly and would reject a reason backed by words that are not in the message; whether that happened in this run was not recorded. It is not a fix for the measured problem.
